# Continuous integration (v0.9)

One workflow, `.github/workflows/jade-and-ember-verify.yml`, approved for the v0.9 development branch (decision D-4, `APR-JE-019`; scope `APR-JE-022`). It runs the engineering checks and reports. **It is read-only: it deploys nothing, merges nothing, publishes nothing, has no secrets and makes no call to any paid or AI service.** `check:ci` (part of `npm run verify`) fails if the workflow stops being so.

## Since G6-8 (`APR-JE-049`): the snapshot caller

The workflow file is no longer written out job by job. It is the **snapshot caller** rendered from the framework's template (`node engineering/tools/ci/render.mjs snapshot-caller --project-dir jade-and-ember --branch feature/jade-and-ember-v0.9`): the same seven jobs, with the same names, runners and timeouts, each a pinned checkout (full history, no stored credentials) and one use of the **composite action** that sits in this repository, `./.github/actions/engineering` (modes `verify`, `fast`, `firefox`, `webkit`, `external-links`, `lighthouse`, `supply-chain-report`). The table below describes what each job does; since G6-8 the steps are the action's, not this file's. This repository is public and cannot download the framework's private action, so the action and the engine it runs, `engineering/` at the repository root, are a verified **snapshot** (copy) of the framework's files at framework commit `23fafcd0365ef01aa2460cbb6a31beef8519f802` (git tree `a7ac4a6f4cb6050bcd7fc6b81d62cc3565a5c482`, 249 files, 2,297,963 bytes; the corrected snapshot the owner approved in `APR-JE-050`, which replaced the first one, tree `7a4f8a09d8b4ecbd5b940049d5a1192445e9541c`, because two of its files could not pass the release dry run and the determinism self-test in this layout). `sts-framework-snapshot.json` lists every file with its checksum; the action verifies the copy against it before anything runs, and `check:extraction` verifies it again inside `npm run verify`. The record proves the copy equals the record; only the private framework repository can prove the record equals the framework commit (`tools/snapshot.mjs verify --against <framework checkout>`). The direct style of workflow that G6-7 allowed for this repository is no longer accepted for it: `check:ci` refuses it. `.github/actions/engineering/` and `engineering/` are changed only by a reviewed refresh made by the snapshot tool, never by hand. The project's own records, overlays, checks and the frozen release-control proof of concept stay in this folder.

## The verification record and CI evidence (G6-2, `APR-JE-039`)
`npm run verify` ends by writing a sealed **verification record** (`engineering/.reports/verify.json`) and printing one line at the end of the Verify job log: `verification record: full run, candidate <64 hex>, engine <16 hex>…, <n> checks, seal <64 hex>`. The record is bound to the **candidate artifact digest** (not to the commit), to the digest of the verifying code (`engineDigest`) and to the list of every check `verify.mjs` defines (`registryDigest`); a run that was not full, did not list every check, failed one, or found the artifact or the code changing while it ran, does not produce a record the gate accepts. A person (or a later tool) copies the candidate, `engineDigest`, `registryDigest`, the check counts, the seal and the run id from that line into the `verification` block of a `ci-run` evidence record (`npm run evidence:new -- ci-run`), which `check:release` and the gate compare with what a full run of the **current** verifier must produce. The CI log is therefore the independent place to compare a record against; the gate itself stays offline and never calls the GitHub API.

## Cross-browser verification (Gate 5, Phase 1)
**What runs.** Two informational jobs run the browser-driven checks of `npm run verify` inside Firefox and WebKit with the **same assertions** as the Chromium job: `media`, `seo` (browser part), `privacy`, `security` (CSP under the headers), `d11`, `assets` (hashed copy equal to v0.8), `keyboard`, `reflow`, `forced-colors`, `a11y-tree`, `order`, `phone`, `portability` and `regression` (candidate against the frozen v0.8 baseline, **both rendered in the same engine in the same run**). The command is `node engineering/cross-browser.mjs --engine firefox|webkit|chromium [--only check:a,check:b]`; it never touches `.reports/verify.json`, which the release gate binds.

**Nothing is skipped silently.** `engineering/lib/cross-catalogue.mjs` classifies every check of `verify.mjs` as `engine` (runs in each engine), `static` (no browser; identical in every engine; run once in the Chromium job) or `chromium-only` (with its reason). Each job ends with a matrix of **all** checks for its engine: PASS, FAIL, N/A with the reason, or MISSING (a runner defect). `check:selftest-gate5` fails if a check exists that is not classified, if a browser-driven check has no runner, or if the matrix omits a row. The only `chromium-only` browser check is `budgets` (it needs the Chromium DevTools protocol throttling and the Event Timing, LCP and long-task APIs), so **performance in Firefox and WebKit is not measured by automation**.

**Adaptations are reported.** Playwright cannot honour every option in every engine (Firefox has no `isMobile` context option). The launcher removes only such an option, counts it, and the runner prints `ADAPTED: ...` under the check that needed it; baseline and candidate always get the same adapted options. `forced-colors` first probes whether the engine activates forced-colours emulation and reports **NOT APPLICABLE with the evidence** if it does not (a coverage gap needing a human, not a pass).

**D-11 is tested explicitly** by `check:d11` (it also runs in the Chromium job): every element with a style attribute must resolve the same custom properties and `object-position` with the security headers on as with no headers (desktop and phone width), with no style violation, and an unlisted inline style set by script must be blocked (so "honoured" cannot mean "CSP off").

**Reading a result.** Open the job log; the capability block at the top lists the engine version, video support (`canPlayType` for WebM VP9, WebM VP8, MP4 H.264) and which CSS features `styles.css` uses are supported; then each check with its notes and problems; the matrix and the one-line count at the end. A failure is **evidence about that engine, not a verdict**: a person reviews it and records it in `findings.json` (with a proposal if a visible change would be needed; no visual change without the owner's approval). The jobs become required only when the owner says so.

**Requirements.** Playwright downloads the browsers at run time (`npx playwright install --with-deps firefox`/`webkit`); no change to `package-lock.json`, no new npm dependency. Firefox and WebKit cannot be installed in the development sandbox (their download host is unreachable), so these jobs are the only place they run. The runner stops a check after 12 minutes (`--timeout-minutes`) and reports it as a failure, so one hang cannot stall the job.

**Results and findings so far (run 14, `8556d4f`).** Firefox 157.0: 14 of 14 browser-driven checks pass. WebKit 27.2 (Playwright's Linux build, not Safari): 13 of 14 pass. The CSP is honoured in both engines: `check:d11` shows all 12 element states (every inline style attribute, desktop and phone) resolving identically with and without the headers, and an unlisted inline style is blocked. `check:regression` against the frozen v0.8 baseline, rendered by the same engine, reports no differences in Firefox or WebKit. Engine differences are recorded in `findings.json` with an `engines` field (a finding is expected only in the engines it names, and is NEW, so it fails, anywhere else):
- F-G5-01 (WebKit, file:// only): web fonts are refused from an opaque origin, so the fallback fonts show; over http they load.
- F-G5-02 (Firefox, info): a console warning for the media-qualified hero preload that does not match the viewport. Filtered only in Firefox, counted and reported in `security`, `seo` and `portability`.
- F-G5-03 (Firefox, info): the scrolling category strip on the Menu page at phone width is one extra Tab stop.
- F-G5-04 (WebKit): text-spacing override makes the first Visit hours row's day label and hours overlap at 1440 px. Cause not yet diagnosed.
Harness adaptations (not findings): Firefox has no `isMobile` context option (dropped, reported as `ADAPTED`); Firefox keeps focus on the last element at the end of the document (read as the end of the page, only there); `check:budgets` is not run in Firefox/WebKit because it needs the Chromium DevTools protocol and Event Timing, LCP and long-task APIs (the Chromium job keeps the budgets unchanged).

**Gate 5 diagnostic steps (removed).** During the Phase 1 review the Firefox and WebKit jobs briefly ran `node engineering/tools/gate5-diagnose.mjs --engine <engine>` (investigation only, no artifact upload action). The steps were removed after the correction was verified (APR-JE-029). The script, its screenshots and measurements (`engineering/evidence/gate5-phase1-review/`) and the investigation report (`GATE-5-PHASE-1-REVIEW-INVESTIGATION.md`) stay in the repository; run the script by hand with `node engineering/tools/gate5-diagnose.mjs --engine <engine>` if the behaviour is ever in doubt.

**The WebKit text-spacing correction and what keeps it honest (APR-JE-029).** `styles.css` carries one rule, `@supports (hanging-punctuation:first){.hours th{white-space:normal;min-width:max-content}}`, approved as the correction for F-G5-04; `immutability-allowlist.json` entry IMM-1 is the only source difference from v0.8. `check:regression` accepts the matching computed-style difference **only in WebKit and only on the hours-table `th`** (`approved-style-differences.json`, entry ASD-1: listed properties, exact values for the wrap properties, unchanged position and size); the same difference in Chromium or Firefox, or any other change, fails. `check:supports` (every engine, including the Chromium job) compares each engine's answer for `hanging-punctuation` and the rule's effect with `engine-features.json`, so a new browser or Playwright build that changes where the rule applies is reported. `check:reflow` measures text spacing at 390, 1024, 1100, 1280 and 1440 px in every engine.

## Safety properties (enforced by `check:ci`)
- `permissions: contents: read` at the top level, and no job widens it; the checkout does not persist credentials.
- Every `uses:` is pinned to a full commit SHA (version in the comment): `actions/checkout` v7.0.1 (`3d3c42e5…`) and `actions/setup-node` v7.0.0 (`82076278…`) only, both on the Node 24 runtime. The SHAs are recorded with their verification in `dependencies.json` (`actions`); `check:ci` refuses any other action, any other SHA and a moving tag (G6-1, `APR-JE-038`).
- One Node baseline: `environment.json` (`nodeBaseline`) records the exact tested patch (24.21.0, npm 11.19.0); every `setup-node` step must pin exactly that, `package.json` `engines.node` (`>=24.8.0 <25`) must accept it and equal `environment.json`, and `check:deps` proves it satisfies the `engines` range of every locked package. The blocking job's name states its Node major and `check:ci` refuses a name that disagrees.
- No `pull_request_target`, no `workflow_run`, no `secrets` context, no expression inside a `run:` script (no script injection), no `git push`, no `gh` CLI, no publish, deploy, Pages, cloud or container-registry step, no AI or LLM service or key.
- Every job has a timeout; the blocking job has no `continue-on-error`; dependencies are installed with `npm ci` from the lockfile, with `--ignore-scripts --engine-strict` (a package that does not support the pinned Node fails the install instead of warning).
- `STS_REQUIRE_AUDIT=1` makes `check:deps` fail if `npm audit` cannot reach the registry, so the audit cannot silently be skipped in CI.

## Runner requirements (to reproduce a CI run)
- Git history for all branches (`fetch-depth: 0`): `check:baseline` reads the frozen v0.8 baseline branch `baseline/jade-and-ember-v0.8` and the regression harness exports it. The workflow never writes to it.
- Node 24.21.0 exactly (the Node 24 "Krypton" long-term-support line; npm 11.19.0 ships with it; `engines.node` is `>=24.8.0 <25` because html-validate needs 24.8.0 or later); the exact Playwright (1.64.0) and every other tool come from `package-lock.json`.
- Chromium for Playwright. The reference environment recorded in `environment.json` is Chromium 141.0.7390.37; Playwright 1.64.0's own download is Chromium 156. Baseline and candidate are always rendered by the same browser in the same run, so the comparison holds on either; the pinned version is reported as a note (`--strict-env` would fail on a different build, and CI does not use it).
- ffmpeg on the PATH for the flash proxy (without it the check skips that step and says so).
- Network access to the npm registry for `npm ci` and `npm audit`.
- Python 3 is not needed by `npm run verify`.

## Interaction latency investigation (Gate 4 review decision 1)
**The question.** Run 3 measured 567 to 746 ms for opening the phone menu on the GitHub runner, 6 to 30 ms on the development machine, with the main thread idle (blocking time 5 ms). The budget therefore gates the page's own handler time (`budgets.json`, `interactionMs`, limit 200 ms) and **retains and reports end-to-end latency** (`endToEndMs`, the Event Timing duration: input delay + handler + presentation) as a number that is not gated. The 200 ms INP "good" reference is printed next to it and a note says when it is exceeded.

**The tool.** `engineering/tools/latency-probe.mjs` (investigation only, exit code always 0) opens the phone menu on two pages for each combination of conditions (plain, CPU x4, network emulation, both = the budget profile) and dispatch methods (Playwright click, raw mouse click, touch tap), and records input delay, handler time, time to the next frame, the Event Timing duration, the longest gap of a 4 ms timer chain on the main thread during the interaction, and long tasks. Reading it: a small handler and a small main-thread gap with a large input delay mean the delay is outside the page.

**Local result (development machine, Chromium 141.0.7390.37, 3 repetitions x 2 pages per cell).** Input delay at most 35 ms (median 2 to 28 ms), handler 0.1 to 3.8 ms, event duration 0 to 80 ms in every condition, including the budget profile. The delay seen on the runner does **not** reproduce here, in any condition or dispatch method, so it cannot be explained from this machine.

**What runs 6 and 7 showed.** The long delay exists inside `check:budgets` and does not exist in the probe's plain click, with the same conditions on the same runner. The budget check differs by pressing Escape 150 ms after the click and by Playwright moving the mouse first (the Event Timing list begins with `pointerover`, `pointerenter`, `mouseover`). With an idle main thread the delay is not the page's code. Run 7 answered the open question of *which event*: it is **`pointerover`**, the hover event Playwright's mouse move produces before `pointerdown`. The page has no listener for `pointerover`, `mouseover` or `pointerenter` (checked in `site.js`, `hero.js`, `menu.js`), so no page code runs for it: the 771 ms is the wait before the browser dispatches a synthetic hover event, not anything the website does. It is the same figure on three runs (751, 771 ms and run 3's 567 to 746 ms), so it is deterministic, not runner noise, and it is absent from a probe that issues the identical events on the same runner with the same throttling. What differs is only the budget check's set-up, which the next experiment isolates. The budget check now prints the slowest event and the probe replays the budget sequence and prints each event's delay, handler time and duration. The result is in the run 7 rows below.

**On the runner (historical).** Until run 10 the workflow ran the probe as the last step of the `verify` job (`if: always()`, never failing the build); its output is in the job logs of runs 6 to 10 under "Interaction latency probe" and its results are recorded in the table below. **The step was removed in the post-Gate 4 housekeeping commit** (see "Housekeeping" below); the cause remains unproven.

**Result of the isolation.** None of the three set-up details the probe could add reproduces the delay, and neither do all three together. The delay is therefore **not** caused by the page, by the Escape key, by the response-body hook, by the test server, or by the budget check's observer script. It remains in the budget check when it runs inside `npm run verify` and is absent from a fresh process that issues the same events minutes later on the same runner. Candidates still open: (a) state of the long-running `verify` process or contention from something an earlier check left running while `check:budgets` runs; (b) a difference in how the budget check itself is driven that the probe does not copy (it loads all five pages, sets the pinned locale and time zone, and reads every response body); (c) the runner at that moment. One idea was tested and rejected locally: that the slow `pointerover` is a hover event the browser raises during page load (before the click): with the budget's own observer no event is recorded before the click (the first `pointerover` is at the click). **Cause still unproven.**

**Status (owner decision, `APR-JE-025`): open, non-blocking diagnostic.** The cause is not proven. No further experiment is to be run and no threshold is to be relaxed. The proposal that was waiting for approval (let the probe call the budget check's own measurement function in a fresh process after `verify`) is **withdrawn, not authorised**. Gate 5 may revisit this with real-device traces, where it is first known whether any visitor sees such a delay.

**What this means for the budget.** The handler-time limit (200 ms; measured 2 ms on the runner) is unaffected. The end-to-end figure stays retained and reported, not gated, as decided; it is 784 ms in the CI job and 40 to 56 ms locally. No threshold has been changed on the strength of this investigation.

Controlled follow-ups, none run and none authorised: the same probe on the same runner image with the pinned Chromium 141 instead of the runner's 156 (to separate browser version from machine); with `--headless=new` against the headless shell; with a quiet runner (`concurrency` limits) to rule out noisy neighbours; and, if the delay is in the input path, whether it appears in real-device traces at all (it is a lab artefact until a real device shows it).
