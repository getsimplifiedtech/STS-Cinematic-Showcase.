# Security, privacy and delivery modes (v0.9 Gate 3)

Policy source of truth: `security.json` (headers and Content Security Policy), `privacy.json`, `dependencies.json`. Checks: `check:security`, `check:privacy`, `check:deps`, `check:secrets`. Decision D-5 (`APR-JE-019`): a practical, restrictive CSP; no unnecessary refactoring; any visual or functional impact reported before an affected change is made. **No page, style, script or asset was changed for this gate**: the policy is generated to fit the pages exactly as they are.

## 1. What protects the site in each delivery mode
| Protection | Served over HTTP(S) with the generated headers | Opened as files (`file://`) from the folder |
|---|---|---|
| Content Security Policy (blocks injected script, inline handlers, foreign scripts, styles, images, frames) | **Yes**, as a header. Proven by probes: an injected inline script, an inline handler, an external script, an unlisted inline style, an iframe and an external image are all blocked | **No.** There are no headers over `file://`, and the pages carry no CSP meta tag (a meta tag would change the delivered pages, and `'self'` is unreliable for `file:` documents). The same injected script **runs** (the check demonstrates it) |
| `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` | Yes | No |
| Clickjacking (`frame-ancestors 'none'`, `X-Frame-Options: DENY`) | Yes (headers only; a meta CSP cannot set `frame-ancestors`) | Not applicable |
| HSTS and `upgrade-insecure-requests` | Yes, HTTPS deployments only (they are in the HTTPS variant of the files) | Not applicable |
| Nothing leaves the visitor's browser: no third-party request, no cookie, no storage, no analytics, no form, no `fetch`, no dynamic code (`check:privacy`) | Yes, by construction | **Yes, the same**: this is a property of the files |
| New-tab links are `noopener noreferrer`; outbound links only to listed hosts | Yes, in the markup | Yes, in the markup |
| Integrity of the delivered bytes (`assets.manifest.json`, `check:assets`) | Yes | Yes |

**Reading it plainly.** Over `file://` the site is safe because it is inert (static files that call nowhere), not because a browser enforces a policy on it. A folder someone has altered is not protected by anything here: the delivered folder is meant to be opened from a source the visitor trusts (the preview package carries `SHA256SUMS`-style checks in `baselines/`). Over HTTP(S) the headers add enforcement, which is what a deployment should use.

## 2. The Content Security Policy
Generated by `engineering/tools/host-files.mjs` from `security.json` and the freshly built pages (`npm run host:files`):

```
default-src 'none'; script-src 'self' 'sha256-<inline bootstrap>'; style-src 'self';
style-src-attr 'unsafe-hashes' 'sha256-<each inline style value>'; img-src 'self' data:; font-src 'self'; media-src 'self';
connect-src 'none'; manifest-src 'none'; worker-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none';
frame-ancestors 'none'                      (+ upgrade-insecure-requests on HTTPS)
```
- **No `'unsafe-inline'`, no `'unsafe-eval'`, no wildcard, no `http:` or `https:` source, no `blob:`.** `data:` only for images (the inline favicon).
- **The one inline script** (`document.documentElement.className+=' js'`, 41 bytes, on every page) is allowed by its SHA-256 hash.
- **The six inline `style` attributes** (the custom properties `--pos`, `--focus-d`, `--focus-m` that set where each photograph is cropped, on Home and Menu) are allowed by hash through `style-src-attr 'unsafe-hashes'`, not by `'unsafe-inline'`. The hashes depend on the configuration: regenerate the files after every rebuild; `check:security` fails if the hashes do not cover exactly what the pages contain (none missing, none left over).
- **Verified impact: none.** The candidate served with these headers is identical to v0.8 served without them: text, accessibility tree, computed style and geometry of every element, and screenshots at 1440, 820 and 390 px (60 comparisons, 0 differences); 10 page loads with the hero video, Pause and the phone menu raise no violation and no console message.

### Decision for the owner: D-11, how to keep the six inline styles working under the CSP
The policy relies on `'unsafe-hashes'` in `style-src-attr`. Chromium supports it and the checks here prove it. **I could not test Firefox or Safari.** A browser that did not honour it would block the six inline custom properties: the browser would still show every photograph, but at its default crop instead of the approved focal points (a visible degradation, on Home and Menu only). Two choices:
1. **Keep the hashes (current, nothing to change).** Recommended while testing continues; add Firefox and WebKit to the browser matrix (Gate 5, decision D-9) before any deployment.
2. **Remove the dependency**: have the build write the six values into the stylesheet as classes (for example `.pos-1 { --pos: 58% 52% }`) and drop the style attributes, so the policy needs no `style-src-attr` at all. The harness would prove the computed styles and pixels identical. It changes the HTML bytes of two pages and adds a small amount of CSS: it is a refactor of delivered files, so it is not done without your decision.

## 3. Headers and hosting
`npm run host:files -- --out host [--prefix /subdir] [--http]` writes `_headers` (Netlify, Cloudflare Pages), `nginx.conf`, `htaccess` (Apache, mod_headers), `csp-meta.html` (a weaker fallback for a host that cannot send headers: not added to the pages; it cannot carry `frame-ancestors`) and `HOSTING.txt`. All three renderings carry the same headers (checked). Cache rules: HTML, CSS and JS `no-cache` (revalidate); fonts and media one week; **nothing is `immutable` because file names are not content-hashed**. For long-lived caching deploy the hashed copy (`npm run build:hashed`, ledger ENG-065): every CSS, JS, font and media file renamed `name.<8 hex>.ext`, every reference rewritten, equal to v0.8 in the browser. Deploy one of the two, never both. Nothing here deploys anything.

## 4. Other checks
- **Privacy** (`check:privacy`): no cookie, storage, service worker, beacon, fetch, geolocation, media device, fingerprinting read, third-party resource, preconnect or `@import`; outbound links only to `getsimplifiedtech.com` plus the client's own ordering and map URLs from configuration. Verified statically in every script and in the browser in 10 page loads.
- **Dependencies** (`check:deps`): no runtime dependencies at all; 7 development tools pinned exactly; lockfile from the npm registry with sha512 for 341 packages; licences from an allow-list (one package, `parse-cache-control`, records no licence: reported as **unverified**, never assumed); `npm audit`: 0 production vulnerabilities, 0 critical, 11 high in the development-only tree of Lighthouse CI (`@lhci/cli`, used by `npm run test:lighthouse`, not part of `verify`, never delivered), each recorded in `dependencies.json` and reported on every run.
- **Secrets** (`check:secrets`): the working tree and the added lines of every commit scanned for 11 credential patterns; the workflow may not read the `secrets` context.
- **CI** (`check:ci`, `CI.md`): read-only workflow, minimal permissions, no deployment, no merge, no secrets, no AI service, pinned actions, `npm ci --ignore-scripts`.
