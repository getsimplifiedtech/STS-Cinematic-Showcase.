## 3. V3 in detail (summary; the evidence is in the private framework repository)

The template is a single page with chapters and two themes. It was read with `git archive`, never checked out; the engineering was a copy of the framework head; the scaffold (a manifest declaring the selectors the template's markup really has, a build wrapper, a workflow, and the generic fixture's overlays and records, which are invented) was added **next to** the template's files, and a script compares all 36 template files byte for byte afterwards (regular files only). The creative authority record is the fixture's, unchanged; `check:authority` passing on it says nothing about the template.

**Correction of the first draft.** The first V3 document and the first version of this section were wrong, and an independent review found it: my scaffold had declared every selector null, so "core finding C3" (a page without a navigation toggle cannot be expressed) was an artefact of the scaffold and is withdrawn; fast-tier and full-tier numbers were mixed; failures caused by the fixture's invented overlays were counted as template findings. The figures here are from the corrected full-tier run.

Of the 25 failures, by primary cause:

* **Template findings** (it does not meet rules the engineering enforces): dependency pinning, no `engines.node`, a retired dependency with 17 advisories; inline styles, an inline handler and a form against the security policy; an `aria-hidden` container with focusable content; committed pages that say v0.3.1 while a fresh build renders v0.3.0; hero clipping at 320 px.
* **Onboarding** every new project has to do: a `verify` script, generated procedures, a project-owned client-build recipe, a `config/client.json`, real budgets (the overlay used was the fixture's invented one, so the budget figures are not the template's).
* **By design**: the five per-project self-tests are bound to a project's own markup and are not applicable to another structure.
* **Defects or limits of the core.** Ten, all fail-closed or over-reporting, none a safety hole. I checked each in the code except where marked:

| # | Core finding | Kind |
|---|---|---|
| C1 | The delivered-media digest crashes (`EISDIR`) on a nested asset folder, and the package verifier hard-codes flat `media/` and `fonts/` folders, so fixing the digest alone moves the failure | robustness; blocks a release of such a site |

(C4, the per-project self-tests, is the by-design item above; C3 is withdrawn.)

What V3 shows: the core ran on a structure that is not a restaurant and not the fixture, with no change to the core, and failed closed where it did not fit. That is evidence the core is not tied to Jade & Ember. It is weaker evidence for "the policy is profile-driven": several checks could not be evaluated without a project-owned client-build recipe and five suites are not applicable to another structure. **Adoption constraints (conditional on the project):** a site with sub-folders in `media/` or `fonts/` cannot be released until C1 is fixed (it needs a snapshot change and renewed approval); a project must supply the files listed above. None of this is a defect of the delivered Jade & Ember.

**Optional improvements** (none needed to close G6-8; each needs the owner's approval because it touches an approved snapshot file, adds a check or changes a workflow): assert the dry run's not-applicable count (risk 1); pin suite case counts (2); scan the project's engineering folder, adapters and generators for network and deploy calls (3); a private-side verification job on the public repository (5); snapshot-caller dry-run scenarios (note under section 4); run `gate6:scope` and `gate5:closure` in CI (section 6); an adoption guide; the core fixes above.
