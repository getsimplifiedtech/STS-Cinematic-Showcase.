# Hosting: static folder, Cloudflare Pages, no vendor lock-in

The deliverable is a **plain static folder**: five HTML pages, `styles.css`, three scripts, fonts and media (23 files in the demonstration; a client build adds `robots.txt` and `sitemap.xml`). It opens from `file://`, from any web server, and from Cloudflare Pages. Nothing in it needs Node.js, a build service, a function, a redirect rule or a vendor account. **Functionality is independent of Vercel**, and of every other host: no file, script, configuration or engineering rule depends on Vercel (`check:hosting` fails if one does).

Nothing in this repository deploys anything. Deployment of any build needs a recorded release approval (`APPROVALS`, section B) and, for a client, the release gate below.

## Cloudflare Pages settings (the deployment model Gate 4 preserves)

| Setting | Value |
|---|---|
| Framework preset | None |
| Build command | none for the committed folder, or `node build.mjs` when building from `config/` |
| Build output directory | `jade-and-ember/` (the folder that holds `index.html`), or the folder given to `node build.mjs --out` |
| Headers | copy `_headers` generated by `npm run host:files -- --out host` into the output folder (a build step is not needed; it is a file) |
| Environment variables | none |
| Functions, `_worker.js`, `_routes.json`, `_redirects`, `wrangler.toml` | none. `check:hosting` fails if any of them appears in the delivered folder |

Pretty URLs (`/menu` for `/menu.html`) are done by Cloudflare Pages itself; the pages use relative links and work either way (`check:portability`: domain root, sub-folder, extension-less URLs). Under a sub-path, `npm run host:files -- --prefix /sub` writes the `_headers` rules under that prefix.

## Limits `check:hosting` enforces (Cloudflare Pages documentation)

| Limit | Value | Where it is checked |
|---|---|---|
| Files in a deployment | 20,000 | folder walk (the site has 23 to 27) |
| Size of one file | 25 MiB | folder walk (the largest file, the hero video, is a small fraction of the limit) |
| Rules in `_headers` | 100 | generated file (about 7) |
| Length of one `_headers` line | 2,000 characters | generated file (the CSP line is the longest) |

Cloudflare joins the values of every matching `_headers` rule instead of replacing them, so the generated file puts the security headers only in the `/*` rule and `Cache-Control` only in the narrower rules; the check fails if a header appears twice or `immutable` is used for names that are not content-hashed.

## What `check:hosting` proves

1. The demonstration and a realistic client build contain only static web files, an `index.html`, no application, function, redirect, vendor or secret files; the demonstration has no `sitemap.xml` or `robots.txt`, the indexable client build has both.
2. No source, configuration, delivered file or engineering rule refers to Vercel; no site script makes a network call.
3. `_headers` generated for both builds, at the domain root and under a sub-path, parse as valid rules within the limits above and carry the CSP computed from the built pages.

## What it does not prove

- That Cloudflare Pages accepts the folder: nothing here contacts Cloudflare. A first deployment (after approval) should be a **preview** deployment that is checked in the browser with the headers on (look for CSP violations in the console and open every page).
- Behaviour in Firefox and WebKit under the headers (decision D-11: test them before production deployment).
- The result of TLS, DNS, caching or the host's redirects.

## Release gate in one paragraph

`npm run release:gate` evaluates a build against `release/policy.json`. The demonstration may be released only while it stays `noindex` and carries its fictional disclosures, and it has no deployment approval today. A **client-production** build is blocked unless: the working tree is clean; a full `npm run verify` passed for exactly this commit and these delivered bytes; there is no open Blocker or Major finding; the version is stable (no `-dev`, `-rc`); a release approval record names this client, version and commit; media rights are verified by the owner against named sources; and real-device, screen-reader, browser-matrix and CI-run evidence exist for this commit (`engineering/release/evidence/`). `npm run release:manifest` writes the manifest (version, source commit, framework reference, configuration hashes, asset integrity, QA status, required and recorded approvals). Both commands only read and report.
