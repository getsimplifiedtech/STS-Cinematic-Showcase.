Quotations are exact. **Facts** are statements about what the specifications say or what Jade & Ember does today; **recommendations** are marked R.

## 3. The two owner rulings and the two extensions

**(a) Builder scope (rule).** The architecture's compiler produces a "builder-facing specification" for Lovable ("Lovable remains the builder and should receive only resolved, validated project specifications"). Jade & Ember and the framework's own template render with a deterministic Node build and no Lovable. The engineering has no stake in the choice (R-01: it verifies the delivered folder), but the architecture should say whether a deterministic static build is a sanctioned builder path, because the release manifest then stands in for the lockfile of step 13.

**(b) Visual packages beside the creative authority (rule).** The architecture defines aesthetic packages ("Editorial; Professional; Luxury/Premium; ... Warm Contemporary") with a package contract and compatibility matrix. The pin makes the Anthropic Frontend Design skill the creative authority and retires the earlier STS skill. The specifications do not say which governs when a package's grammar and the authority's brief disagree. The engineering framework takes no position: it neither selects a package nor judges taste (R-03).

**(c) Extension to spec 15 (extend).** Add `status` (`approved`, `rejected`, `revoked`, `superseded`), `reviewer authorisation` (who may approve which type) and `revocation` (who, when, why, effect on dependants), keeping the content-hash binding and "forbidden cannot be approved away". This is exactly Gate 6 priority 2 expressed in the framework's own terms.

**(d) Engineering namespace (extend).** Register engineering check and adapter ids under the `qa.` framework-meta namespace of spec 11, so the engineering is addressable without becoming a layer.

Neither extension is an edit: both are proposals to be put through the framework's review process (the framework README describes independent review with findings classed as blockers, major, minor, optional) after the owner approves proposing them (D-P8-3).

## 4. What this means for the migration

- **R** No specification needs to change for the engineering to be extracted; two would benefit from additions (c, d) before Gate 6's release model is finalised, because the model reuses spec 15's shape.
- **R** The framework's own README is out of date (10 specifications listed, 15 present, "do not begin destructive migration"). Updating it is a framework change and belongs to G6-0 under the owner's approval.
- **R** Spec 14's Framework Release is the natural carrier of the engineering version. Until one exists, clients pin a commit.
- **Fact** The framework has no engineering code today; it will gain a top-level `engineering/` (proposal D-P8-1) rather than altering any existing document.
