## 4. Production-domain safeguards and prevention of fictional-business indexing

The fictional restaurant is defended in layers; each layer is tested and none depends on the others.

| Layer | What it does | Tested by |
|---|---|---|
| 1 Configuration | `flags.demo true` requires `seo.noindex true`; the build refuses otherwise | `seo config: the demonstration made indexable` |
| 2 Output | the demonstration emits no canonical, `og:url`, JSON-LD, `sitemap.xml`, `robots.txt`, `llms.txt` | `check:seo`, `check:hosting`, `metadata: a noindex page carries og:url`, `llms: the fictional demonstration must not publish llms.txt`, `hosting: the demonstration publishes a sitemap` |
| 3 Pages | `<meta name="robots" content="noindex, nofollow">` on all five pages | `check:seo` |
| 4 **Response header (new)** | `X-Robots-Tag: noindex, nofollow` in `/*` of `_headers`, and in nginx and Apache, generated from `security.json` `noindexHeaders` only when every built page is noindex; never in an indexable build; a build with some noindex pages is refused | `check:hosting` (`checkHeadersFile`), `check:security`, 6 negative tests (header missing, another value, repeated in a second rule, present in an indexable build, only some pages noindex, a mixed build gets no host file) and one that must find nothing (demonstration and client are told apart) |
| 5 Release gate | `demoStaysNoindex`; a demonstration can never be released as client-production; `noDemoText` | `check:release` single-defect cases |
| 6 Production domain | `productionDomain` refuses reserved, example, local, preview and staging hosts (`*.test`, `example.com`, `localhost`, IPs, `*.pages.dev`, `*.vercel.app`, `*.netlify.app`, `*.github.io`, labels such as `staging`) | `check:seo` (15 hosts recognised, 4 real-looking domains not flagged), `check:release` (pages.dev, vercel.app, more) |
| 7 Human | `search-review` approval bound to the artifact digest; `releaseApproval`; `rightsVerification` | none exists; none may be written for work not done |

Limits, stated: the header protects the demonstration only where a host is configured with the generated file (`hosting/`: Gate 6 adapters must write it for Cloudflare Pages and Vercel); `robots.txt` is deliberately absent from the demonstration, so on Cloudflare Pages a request for it would receive the home page unless a proper 404 exists (decision D-P3-1, risk HR-01); no layer can make an external system forget a page it already fetched.

## 6. `og:image` and social preview images

Current state: `og:title`, `og:description`, `og:type` and (indexable only) `og:url` are generated. **No `og:image`, no `twitter:image`.** Reasons, all in force:
- The only images are the six generated photographs and two video frames in `media/`. Their rights are **not verified** (`docs/JADE_AND_EMBER_MEDIA_RIGHTS_POLICY.md`; the release gate's `rightsVerification` is unmet), so none may be presented, in markup or in wording, as licensed for sharing.
- A preview image is a different crop (typically 1200 × 630) of licensed media: it would be new media, which this phase may not create; visual proposal VP-4 ("social image and icons") is not approved.

Requirements recorded for when an image is approved (none implemented):
1. A licensed image supplied or approved by the owner, named in a `rightsVerification` approval (source, licence, date).
2. A configured file path (`seo.ogImage`) in the delivered folder, an absolute `https` URL on the production base URL, a size and dimensions on record (1200 × 630 recommended), an alt text, and `og:image:alt`, `og:image:width`, `og:image:height`, `twitter:card` set from the same data.
3. The build refuses an image that does not exist or is outside `media/`; the release gate requires the rights record; no rights wording appears in the page or `llms.txt` (the existing scan already catches such claims).

**New guard:** `metadataProblems` now fails if any page, demonstration or client, declares `og:image`/`twitter:image` (3 negative tests), so an unlicensed preview image cannot slip in. When an image is approved, the guard is replaced by the requirements above in one change.

## 7. The `X-Robots-Tag` defence (item 7)

- **Policy:** `engineering/security.json` `noindexHeaders` (`X-Robots-Tag: noindex, nofollow`), separate from the security headers: it is not part of `securityHeaders()`, the CSP, the simulated servers or the regression comparison, so nothing about page rendering changed.
- **Where it appears:** `host:files` and `release:prepare` output (`_headers` in the `/*` rule, nginx `add_header`, Apache `Header always set`), only when `noindexState(site) === 'all'`, i.e. when the delivered pages say noindex themselves. The state is read from the built bytes, not the configuration, so the header cannot disagree with the pages.
- **Release manifest:** `search.noindexHeader` and `search.crawlerReview` are now recorded (manifest schema updated).
- **Not covered here:** a Vercel rendering does not exist (adapter, Gate 6); live delivery of the header on any host is unverified (`hosting/`).
